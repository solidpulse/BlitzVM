# Native-image validation and WordPress measurements

Requires the already-installed matching GraalVM, Maven, PHP-FPM, and the existing
`nginx:alpine` Docker image. The build/tracing scripts never install tools or
download WordPress. Run from the repository root:

```bash
bin/trace-native.py /path/to/wordpress
bin/build-native.sh
target/blitzvm -Dblitz.bytecode=off script.php
target/blitzvm -Dblitz.bytecode=auto serve --port 18088 --cpus 4 /path/to/wordpress
```

`GRAALVM_HOME` overrides `.graalvm/current`; its version must match `pom.xml`.
Extra native-image build options are accepted as arguments. Default build limits
are four threads and a 6 GiB builder heap. Keep any emitted JDK `.so` files beside
the executable when distributing it. Runtime `-D` flags precede the script or
`serve` command.

The tracing agent runs the full Maven suite in AST and bytecode modes, plus seven
WordPress pages in each mode. **Never run JDBC fixtures against WordPress's
database:** they drop/recreate tables, including `wp_options`. They remain
skipped unless `BLITZ_MYSQL_HOST` and an explicit isolated `BLITZ_MYSQL_DB` are
supplied. The tracing script refuses `wp` and `wpfresh`; other database names
must also be checked by the operator. WordPress requests collect JDBC metadata
without enabling destructive fixtures. `--skip-tests` reuses completed traces.

```bash
bench/native-image.py check /path/to/wordpress
bench/native-image.py measure /path/to/wordpress
bench/native-image.py micro /path/to/wordpress
bench/native-image.py summarize /path/to/wordpress
```

`check` compares response bodies and status codes with JVM AST, then checks every
top-level PHP conformance fixture against its committed `.out`. FPM bodies are
also recorded to expose inherited compatibility differences. Login, RSS, and
other pages are compared without masking; any dynamic difference is reported.

`measure` runs three repetitions, serially: native AST/bytecode, JVM AST/bytecode,
FPM; then native AST/bytecode after a longer warm-up. Each fresh server warms
`/` for 90 s (long variant: 300 s) and `/wp-load.php` for 30 s at four connections.
It measures boot/front p50 at one connection and front throughput at four,
15 s each. All load is generated by the unchanged `bench/LoadGen.java` with
`-Dwarmup=0 -Dhost=localhost:18088`. FPM uses four static workers, opcache on,
JIT disabled, behind nginx using the templates in `bench/fpm`.

Results and logs go to `target/native-bench`. `--run DIR` selects an independent
result directory, `--port N` a free HTTP port, and `--repeats N` the run count.
`--variant standard|long` splits the measurement schedule. Completed rows are
resumed from JSON; use a **new directory after any binary/configuration change**
to avoid mixing builds. The harness stops only its own PIDs/container ids.

Startup includes the first full WordPress front page, not just listening on a
socket. RSS sums FPM master/workers (shared pages counted multiple times); nginx
RSS is separate. Load averages are captured before every phase, and `uptime`
is included in each raw load log. Differences under shared-machine load should
be judged across alternating pairs, not from one run.
