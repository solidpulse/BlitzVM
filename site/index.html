A faster runtime for PHP.

Every backend hits this eventually: one heavy request ties up a php-fpm worker, and everyone queued behind it waits. BlitzVM's SS Optimizer runs hot code faster than PHP's own JIT and keeps quick requests quick while slow ones run. Each request still starts with clean state, and you write the same plain PHP you would write today.

The numbers

03

You still write plain PHP

Swoole is fast, but you pay for it in how you write code. Your app turns into a long-running server, requests share its memory, and a CPU-heavy handler blocks whichever worker it lands on. I wanted to keep the php-fpm model exactly as it is and make it fast underneath.

Same model as php-fpmOne file per request. $_GET, echo, header() and exit work the way you'd expect. No bootstrap file, no request objects.
No coroutinesYou don't write go(), channels or wait groups. A blocking call is just a blocking call, and other requests keep running while it waits.
Nothing leaks between requestsEvery request starts with a fresh context, so there's no state to reset afterwards. That reset step is exactly what makes Laravel Octane fiddly.
No yielding by handYou don't have to chop a slow loop into pieces or push it off to a task worker. Other requests stay fast either way.

Can't Swoole do this too?

Swoole does have one. Set 'enable_preemptive_scheduler' => true and coroutines get time-sliced every 10 ms. In my tests that answers the hello request about as fast as BlitzVM does, so on that one number it's a tie.

Turning it on also means a coroutine can be paused in the middle of any loop, while every coroutine in the worker shares the app's globals and statics. So a static cache or a singleton that's halfway through being set up can be seen by another request mid-update. It's a big gun, always pointed at your feet. Miss one lock and you get a bug that only shows up under load and never on your laptop. The bigger costs don't go away either: you still have the long-running server, the state you have to reset between requests, and no JIT.

BlitzVM gets the same quick answer without any of that. Its requests work like classic php-fpm: they don't share anything, so there's nothing for them to race on.

WordPress and the Tempest framework already run unmodified, with pages byte-identical to PHP's. Laravel is next.

04

SS Optimizer

BlitzVM's speed comes from the SS Optimizer, its own optimization layer. How it works isn't public yet. What it does is measurable, and every number on this page comes from it.

Hot code beats PHP's own JIT1.2× to 2.5× faster than opcache's tracing JIT on the kernels in fig. 3, with no changes to the PHP.
Slow requests don't block quick onesA quick request is answered in milliseconds while a CPU-heavy one holds the only worker (fig. 1).
Waiting is cheapA request waiting on a database or an API doesn't tie up capacity, so throughput holds up on I/O-heavy pages (fig. 2).
Nothing shared between requestsEvery request starts with clean state, the same guarantee php-fpm gives, without paying to start over each time.
