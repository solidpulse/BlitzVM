A preemptive runtime for server-side languages.

Built around two ideas: no request should be able to starve the others, and no request should see another's state. BlitzVM compiles hot code to machine code, time-slices every request and isolates each one in its own context.

03

Why it is fast

BlitzVM's own parser, interpreter, scheduler, isolation model and HTTP server make the design decisions below. For machine code it uses the Graal compiler as its JIT back end, much as many languages use LLVM. Each decision maps to a number in the benchmarks.

3.1

The interpreter specializes itself, then the JIT compiles it

PHP source is parsed by a hand-written lexer and Pratt parser into a tree of self-specializing nodes. Each node rewrites itself to the types it actually sees. A + that has only seen integers becomes a single machine add with an overflow check, and moves to floating point only when a value overflows, as PHP 8 specifies.

Once a function is hot, the Graal compiler partially evaluates the interpreter together with the specialized tree and emits machine code. Call sites cache their target, so user functions are inlined into their callers. This is why recursive, loop-heavy PHP runs several times faster than opcache, including opcache's own tracing JIT.

// Integer path: one add and an overflow branch.
@Specialization(rewriteOn = ArithmeticException.class)
long doLong(long a, long b) { return Math.addExact(a, b); }

@Specialization
double doDouble(double a, double b) { return a + b; }
3.2

Preemption at guest safepoints, also inside compiled code

A request needs one of N CPU slots to run. A ticker checks the slots every half quantum. When a request has used its 10 ms quantum and others are waiting, the scheduler queues an action on that request's thread. The action runs at the next guest safepoint and hands the slot to the next request in line.

The safepoint checks are compiled into the machine code at loop back-edges and calls, so preemption keeps working after a hot loop has been JIT-compiled. php-fpm cannot do this, because one process serves one request until it finishes. Swoole's default coroutine scheduler switches only at I/O.

3.3

Shared compiled code, private request state

All requests share one engine, which holds the parsed trees and the compiled machine code. Each request gets a fresh context with its own globals, so requests share nothing, as under php-fpm, without re-parsing or re-compiling anything.

CPU time is charged per request. A runaway script is cancelled when it exceeds its budget and gets a PHP-style fatal error, while the process and every other request keep running.

3.4

An epoll front end that never runs guest code

HTTP is parsed by Netty on its native epoll transport. Event-loop threads only read and write sockets, and each request is handed to a worker that waits for a CPU slot. There is one process and one hop, where php-fpm needs nginx, FastCGI and a pool process.

Each connection answers pipelined requests in order from a small queue and stops reading while a request is in flight, which gives the server backpressure against clients that queue unbounded work.

04

How a request becomes machine code

Everything inside the dashed boundary is BlitzVM. The language front end builds self-specializing trees on the Truffle node framework, and the Graal compiler turns hot trees into machine code. The request path around them, the scheduler and the isolation model, does not depend on PHP.

Parse onceThe parsed tree is cached per file on the shared engine and reused by every request until the file changes.
Compile onceCompiled machine code belongs to the engine, so later requests to a hot page start out compiled.
Isolate every requestGlobals, output buffer, headers and CPU budget live in the request's own context, which is discarded afterwards.
05

From PHP to Node.js-compatible environments

The scheduler, the isolation model and the HTTP front end do not depend on PHP. PHP came first because its request model makes scheduling and isolation easy to measure against established servers.

working

PHP 8 core

Functions with defaults and by-reference arguments, copy-on-write arrays, PHP 8 type juggling and integer overflow, alternative syntax, templates, superglobals, headers and status codes, and 179 builtins. Output is checked against PHP 8.5 on a conformance suite.

prototype

Virtual threads for waiting requests

Running request contexts on Java virtual threads makes a sleeping or waiting request almost free. In the prototype, 2,000 requests that each sleep 200 ms finish in , against on a 64-thread pool.

Hot builtins such as strlen, count and microtime rewritten as nodes, so the JIT can inline them into the surrounding code.
