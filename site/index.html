PHP, compiled to machine code and never starved.

BlitzVM runs PHP on GraalVM. Hot code is partially evaluated into machine code, every request runs in its own isolated context, and a preemptive scheduler time-slices CPU-bound requests so one slow script cannot block everyone else.

Why it is fast

Four design decisions, each measurable

Execution

The interpreter specializes itself, then Graal compiles it

PHP source is parsed by a hand-written lexer and Pratt parser into a tree of Truffle nodes. Each node rewrites itself to the types it actually sees. An + that has only seen integers becomes a single machine add with an overflow check, and falls back to floats only if a value overflows, exactly as PHP 8 specifies.

Once a function is hot, Graal partially evaluates the interpreter together with the specialized tree and emits machine code. Call sites cache their target, so user functions are inlined across calls. That is why recursive, loop-heavy PHP runs several times faster than opcache, including opcache's own tracing JIT.

// Integer path: one add and an overflow branch.
@Specialization(rewriteOn = ArithmeticException.class)
long doLong(long a, long b) { return Math.addExact(a, b); }

@Specialization
double doDouble(double a, double b) { return a + b; }
Scheduling

Preemption at guest safepoints, also inside compiled code

A request needs one of N CPU slots to run. A ticker checks every half quantum. When a request has used its 10 ms quantum and others are waiting, the scheduler queues an action on that request's thread. The action runs at the next guest safepoint and hands the slot to the next request in line.

Graal compiles those safepoint checks into the machine code it emits, at loop back-edges and calls, so preemption keeps working after a hot loop has been JIT-compiled. php-fpm cannot do this: one process serves one request until it finishes. Swoole's default coroutine scheduler only switches at I/O.

Isolation

Shared compiled code, private request state

All requests share one engine, which holds the parsed trees and the machine code Graal produced. Each request gets a fresh context with its own globals, so requests share nothing, as under php-fpm, without re-parsing or re-compiling anything.

CPU time is charged per request. A runaway script is cancelled when it exceeds its budget and gets a PHP-style fatal error, while the process and every other request keep running.

Front end

Netty with native epoll, and PHP never runs on the event loop

HTTP is parsed by Netty on its native epoll transport. Event-loop threads only read and write sockets; each request is handed to a worker that waits for a CPU slot. There is one process and one hop, where php-fpm needs nginx, FastCGI and a pool process.

Each connection answers pipelined requests in order from a small queue and stops reading while a request is in flight, which gives the server natural backpressure against clients that queue unbounded work.

Architecture

How a request becomes machine code

The language implementation plugs into Truffle. Graal compiles the specialized tree. The request path around it is the scheduler and the isolation model, which do not depend on PHP.

Parse onceThe parsed tree is cached per file on the shared engine and reused by every request until the file changes.
Compile onceMachine code produced by Graal belongs to the engine, so the second request to a hot page starts out compiled.
Isolate every requestGlobals, output buffer, headers and CPU budget live in the request's own context, which is discarded afterwards.

Roadmap

From PHP to Node.js-compatible environments

The scheduler, the isolation model and the HTTP front end do not depend on PHP. PHP is the first language because its request model makes the scheduling and isolation results easy to measure against established servers.

Working

PHP 8 core

Functions with defaults and by-reference arguments, copy-on-write arrays, PHP 8 type juggling and integer overflow, alternative syntax, templates, superglobals, headers and status codes, and 179 builtins. Output is checked against PHP 8.5 on a conformance suite.

Prototype

Virtual threads for waiting requests

Running request contexts on Java virtual threads lets a sleeping or waiting request cost almost nothing. In the prototype, 2,000 requests that each sleep 200 ms finish in , against on a 64-thread pool.

Next

Builtins as compiled nodes

Hot builtins such as strlen, count and microtime rewritten as Truffle nodes, so Graal can inline them into the surrounding code.

Planned

Node.js-compatible environments

JavaScript workloads on the same core: preemptive time slicing for event-loop code, per-request isolation, and the shared compiled engine.
