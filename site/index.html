BlitzVM
v0.1 research preview

research projectPHP for nowNode.js and Bun later

A preemptive runtime for server-side languages.

Every backend hits this eventually: one heavy request ties up a php-fpm worker, or the whole event loop in Node and Bun, and everyone queued behind it waits. BlitzVM JIT-compiles hot code and preemptively schedules requests in short time slices. Each request still starts with clean state, and you write the same plain PHP or JavaScript handler you would write today.

02

The numbers

All of this ran on one 8-core Linux box with the same PHP files on every server. Everything gets 15 seconds of warm-up before I measure, and where my own runs disagreed I used the slower one. The full setup is in section 07.

03

You still write plain PHP

Swoole is fast, but you pay for it in how you write code. Your app turns into a long-running server, requests share its memory, and a CPU-heavy handler blocks whichever worker it lands on. I wanted to keep the php-fpm model exactly as it is and do the scheduling underneath it.

Same model as php-fpmOne file per request. $_GET, echo, header() and exit work the way you'd expect. No bootstrap file, no request objects.
No coroutinesYou don't write go(), channels or wait groups. A blocking call is just a blocking call, and the scheduler gives the CPU to someone else while it waits.
Nothing leaks between requestsEvery request starts with a fresh context, so there's no state to reset afterwards. That reset step is exactly what makes Laravel Octane fiddly.
No yielding by handYou don't have to chop a slow loop into pieces or push it off to a task worker. It gets paused at the next safepoint either way.

What about Swoole's preemptive mode?

Swoole does have one. Set 'enable_preemptive_scheduler' => true and coroutines get time-sliced every 10 ms. In my tests that answers the hello request about as fast as BlitzVM does, so on that one number it's a tie.

Turning it on also means a coroutine can be paused in the middle of any loop, while every coroutine in the worker shares the app's globals and statics. So a static cache or a singleton that's halfway through being set up can be seen by another request mid-update. It's a big gun, always pointed at your feet. Miss one lock and you get a bug that only shows up under load and never on your laptop. The bigger costs don't go away either: you still have the long-running server, the state you have to reset between requests, and no JIT.

BlitzVM pauses requests at the same kind of points. The difference is that BlitzVM requests work like classic php-fpm: they don't share anything, so there's nothing for them to race on.

To be clear, Laravel doesn't run yet. It needs classes and require, which are next on the list in section 06. When it does run, it should run unchanged.

04

Why it's fast

Most of BlitzVM is custom code: the parser, the interpreter nodes, the scheduler, the isolation and the HTTP layer. For turning hot code into machine code I lean on the Graal compiler, the way plenty of languages lean on LLVM. These are the four things that actually move the numbers.

4.1

The interpreter rewrites itself, then Graal compiles it

PHP goes through a hand-written lexer and a Pratt parser and comes out as a tree of nodes. Each node watches the types that flow through it and specializes. If a + has only ever seen integers, it ends up as one machine add plus an overflow check. If it ever does overflow, it switches to floats, which is what PHP 8 does anyway.

When a function gets hot, Graal compiles the interpreter and the specialized tree together into machine code (partial evaluation). Call sites remember what they call, so small functions get inlined into their callers. That's where the wins over PHP's tracing JIT come from: recursion, integer loops, and code split into lots of little helpers.

// the integer case: one add, one overflow branch
@Specialization(rewriteOn = ArithmeticException.class)
long doLong(long a, long b) { return Math.addExact(a, b); }

@Specialization
double doDouble(double a, double b) { return a + b; }
4.2

Preemption that keeps working after the JIT kicks in

There are N CPU slots, and a request needs one to run. A ticker looks at the slots every 5 ms. If a request has had its 10 ms and someone is waiting, the scheduler queues an action on that request's thread. The action fires at the next safepoint and the slot goes to whoever is next in line.

Those safepoint checks are also in the compiled code, at loop back-edges and calls, so a hot loop can't get away from them. php-fpm can't do this at all, since each process serves one request to the end. Swoole, by default, only switches coroutines at I/O.

4.3

One engine, a fresh context per request

All requests share one engine, which keeps the parsed trees and the machine code. Each request gets its own context with its own globals. So you get php-fpm's shared-nothing behaviour without parsing or compiling anything twice.

CPU time is counted per request as well. If a script blows through its budget it gets cancelled with a normal PHP fatal error, and the process (and everyone else) carries on.

4.4

Netty does the HTTP and never runs PHP

HTTP parsing is Netty on native epoll. The event-loop threads only touch sockets, and every request goes to a worker that waits for a CPU slot. It's one process and one hop. php-fpm needs nginx, FastCGI and a pool process to do the same job.

Pipelined requests on a connection are answered in order, and the connection stops reading while one is in flight. It's a cheap bit of backpressure against clients that try to queue up a pile of work.

05

How it fits together

Everything inside the dashed line is BlitzVM. The PHP front end builds its trees on Truffle's node framework, and Graal compiles the hot ones. The bottom row, the scheduler and the per-request contexts, knows nothing about PHP. That's the reason the Node.js plan is realistic.

Parsed onceEach file's tree is cached on the shared engine until the file changes.
Compiled onceMachine code belongs to the engine, so the next request to a hot page is already compiled.
Thrown away afterGlobals, the output buffer, headers and the CPU budget all live in the request's context, and the context is dropped when the request ends.
06

What's next

None of the scheduling or isolation code is PHP-specific. I started with PHP because it's easy to measure: php-fpm and Swoole are well understood, and the request model is simple. Node.js- and Bun-compatible environments are the bigger target.

working

PHP 8 core

Functions with defaults and by-reference args, copy-on-write arrays, PHP 8 type juggling and int overflow, alternative syntax, templates, superglobals, headers and status codes, and 179 builtins. I check the output against real PHP 8.5 with a conformance suite.

next

Classes, closures and require

What's missing before real apps, Laravel included, can run.

next

Builtins as compiled nodes

Right now strlen, count, microtime and friends are plain Java calls, so the JIT can't see inside them. Turning the hot ones into nodes fixes that.

planned

Node.js- and Bun-compatible environments

A small JavaScript front end already runs on the same core; BlitzVM-JS in the chart at the top is that prototype. Work on full Node.js and Bun compatibility starts once the PHP front end can render Laravel.
