# Task 15 — Bytecode DSL spike

**Outcome:** interpreter-only bytecode is **2.61x faster on `_wp_array_get`**, but only
**1.53x on fifty small functions** and slower on foreach. The **middle decision criterion**
applies: not enough to plan migration on interpreter speed alone. Standalone compiled
`_wp_array_get` is about **5.6–5.8x smaller**; JFR attributes **65.3%** of remaining samples
to frame/operand-stack/local traffic. Results have substantial shared-machine noise;
six interleaved measurements per cell and their spread are reported below.

## Implementation

The spike is isolated in `src/main/java/dev/phpruntime/bc/`. It registers a separate
`php-bc` Truffle language and launches with `bench/bytecode/run-bc.sh`; `bin/php-truffle`,
the AST parser/nodes, dependencies and production runtime are unchanged.

`PhpBytecodeRootNode` uses Truffle 25.5.5.0.3 `@GenerateBytecode`, quickening and
`long`/`double`/`boolean` boxing elimination. Frame locals, constants, structured branches,
loops and returns use the DSL's generated instructions. Arithmetic has typed
specializations and the existing PHP slow paths, including overflow-to-double and integer
results after a previous overflow. Calls cache a `DirectCallNode` to another bytecode root;
argument copying happens before subsequent arguments are evaluated. Function targets are
linked before execution, allowing forward calls and recursion.

The throwaway parser reuses the production **lexer**, not its executable AST. Its temporary
expression/statement records are lowered to bytecode and are never executed. It supports
the requested subset, plus short-circuit boolean expressions, one-level `break/continue`,
`is_int`, `echo` and `hrtime(true)` to run the original WordPress function and instrument
the workloads. Arrays and strings reuse `PhpArray`, `PhpOps`, `PhpNull`, `PhpArith` and
`PhpStrings`; nested writes obey COW, and foreach shares/releases a cursor snapshot with
DSL `TryFinally` cleanup on early exits. There are no fused WordPress-specific operations.
The cached bytecode interpreter is used from the first call; no uncached tier or
instruction-rewriting experiment is included.

This is deliberately not a conforming PHP implementation. References, closures, dynamic
scope/calls, objects, includes and general PHP warning/error behaviour are not implemented.
Missing local/offset reads yield `PhpNull` silently; only array/null offset writes are
supported. `++/--` are rejected. See `bench/bytecode/README.md` for reproduction commands
and the exact subset. Any apparent win is a best-case subset result, not a measured
WordPress request speedup or authorization to migrate.

There are also unavoidable differences beyond the dispatch engine: the spike has static
function links instead of per-context function-table resolution and small specialized
builtin operations instead of the production general builtin argument/dispatch path.
Locals do not carry production dynamic-scope/reference machinery. The experiment measures
this minimal requested path, **not an apples-to-apples replacement of only AST dispatch**;
these simplifications bias in favour of bytecode. Conversely, the production foreach
cursor already loops directly in Java, whereas the spike lowers each cursor step and
assignment into separate bytecode operations.

## Workloads and correctness

| File | Work per measured round | Checksum |
|---|---|---:|
| `01-wp-array-get.php` | 600,000 calls to the WordPress function; alternating fresh 2- and 3-element path arrays | 5,400,000 |
| `02-small-functions.php` | 50 distinct roots, 12,000 round-robin cycles = 600,000 calls; 3 array reads, branch, arithmetic | 3,620,400,000 |
| `03-strings.php` | 600,000 short-string building iterations with `strlen`; reset after 100 iterations | 121,200,000 |
| `04-foreach.php` | 1,000 values, 1,000 foreach traversals, sum by value (also assign keys) | 499,500,000 |

`_wp_array_get`'s executable body is copied from the read-only WordPress source at
`wp-includes/functions.php:5169`; only comments/formatting differ. Untimed checks cover
null/missing/default/invalid/too-deep paths. `check.php` separately exercises COW assignment,
nested writes/appends, by-value function arguments and their evaluation order,
forward calls/recursion/defaults, foreach mutation/continue, break, floats, byte-string
length, equality, overflow followed by small integer operations, and short-circuit side
effects. These are spike-local checks, not new production conformance fixtures.

`python3 bench/bytecode/measure.py --verify` passed against `/usr/bin/php` and both Java
paths, comparing all output except the measured `ns=...` field. Reference output was
generated by PHP, not written by hand.

## Measurement method

Each process runs ten rounds in one context; its measurement is the **median of the last
three rounds** (rounds 7, 8, 9). Reported milliseconds are the median of at least three
independent process measurements, with min–max spread. Processes are interleaved
AST, BC, PHP, AST, BC, PHP, AST, BC, PHP for every workload/configuration. Only one
benchmark process runs at a time; no concurrent Maven/test/profile workload is started.
Parsing, declarations, JVM startup and output are outside the timer. Host JVM warm-up,
guest compilation and GC inside each round remain included.

Both Java paths use the same installed GraalVM and launcher flags, including
`-XX:-DontCompileHugeMethods`. Interpreter-only means **guest Graal compilation disabled**,
not `java -Xint`: HotSpot still compiles Java interpreter/runtime code.

```text
-Dpolyglot.engine.AllowExperimentalOptions=true
-Dpolyglot.engine.Compilation=false
```

Graal-enabled measurements use default compilation thresholds/inlining, no forced
warm-up beyond the prescribed ten rounds. PHP always uses:

```text
/usr/bin/php -d opcache.enable_cli=1 -d opcache.jit=disable
```

The PHP column therefore has the same settings in both Java-mode rows; any difference
between those PHP rows is measurement noise/load, not a PHP JIT switch. Raw rounds,
checksums, stderr and every pre-run `uptime` sample are retained in
`bench/bytecode/results.json`.

## Timings and decision

PHP is **8.5.12**, Zend OPcache **8.5.12**. Java is GraalVM CE
**25.5.5.0.3+1.1**, OpenJDK **25.0.5.0.3**, matching the Truffle dependency version.

The first completed batch is preserved in `bench/bytecode/results.json`, with a readable
table in `bench/bytecode/results-first.md`. One-minute pre-run load was **5.25–9.59**.
It produced interpreter AST/BC ratios of **2.50x, 1.60x, 1.52x, 0.68x** for workloads
1–4. WordPress's three paired ratios were 3.017x, 2.546x, 2.501x; the small-function pairs
were 2.340x, 1.482x, 1.511x. Thus even this batch does **not** meet the 2.5x-on-both
migration threshold. The absolute PHP WP baseline changed from ~90 ms in the interpreter
batch to ~40 ms in the Graal batch despite identical PHP settings, confirming substantial
load effects.

A second complete same-build batch is retained in `bench/bytecode/results-repeat.json`;
no Java source or target classes changed between them. The initial, incomplete command
hit the harness's 120-second timeout; its partial numbers were not used. The completed
batches ran without that overall timeout. In total: **144 serial processes, 1,440 timed
rounds, six process measurements per cell**.

**Shared-machine load:** pre-run one-minute average **4.77–9.59** overall, always above the
instructions' noise threshold of 3. First batch: 5.25–9.59; repeat batch: 4.77–9.59.
All values below include that interference, and the full min–max spread is intentionally
shown. The second batch's WP interpreter PHP baseline dropped 60.75 → 56.55 → 37.41 ms,
while bytecode dropped 602.21 → 664.49 → 333.90 ms; these absolute times are not quiet-machine
estimates. No other agent's processes were killed, reniced or inspected as a workaround.

### Decision criterion

**The middle criterion applies: worth considering only with other gains, not enough to
plan a migration on interpreter speed alone.** Workload 1 clears 2.5x, but workload 2 is
only **1.53x**; the requirement is at least 2.5x on **both**, so it fails. The compiled
workload-2 ratio of 2.51x does not satisfy an interpreter-only criterion.

To reduce dependence on ratios of medians under changing load, the six interleaved
AST/BC paired interpreter ratios are:

| Benchmark | Per-pair speedups | Median paired ratio |
|---|---|---:|
| 1 | 3.017, 2.546, 2.501, 3.604, 2.452, 2.974 | 2.760x |
| 2 | 2.340, 1.482, 1.511, 0.876, 1.496, 1.548 | 1.504x |
| 3 | 1.540, 1.469, 1.422, 1.328, 1.169, 1.412 | 1.417x |
| 4 | 0.657, 0.621, 0.683, 0.662, 0.548, 0.577 | 0.639x |

The same decision holds for each completed batch separately: workload-2 ratio of medians
is 1.60x then 1.50x. One workload-2 pair is actually slower in bytecode, so a uniform
1.5x benefit should not be promised. Foreach is consistently **slower in all six**
interpreter pairs; the current Java cursor loop is already efficient and expanding it
into bytecode adds dispatch. No geometric mean is substituted for the task's two-benchmark
criterion. Array/call overhead remains, and bytecode is still about **9.13x slower than PHP
on workload 1** and **6.68x on workload 2** using the interpreter median columns.

Potential additional gains worth evaluating separately are cold-code memory/uncached-tier
behaviour, serialization/startup and continuation support. They were not measured here
and do not change this spike's conclusion. First pursue runtime array/call/frame costs;
do not infer that changing the execution representation closes the PHP gap.

The first three bytecode traces printed class identities instead of PHP names, because
Truffle's compilation logger uses `RootNode.toString()`. A subsequent **diagnostic-only**
`toString()` override returning the existing name fixed the labels; the three named trace
runs above were collected after rebuilding. No executable operations or benchmark source
changed. The timing table and JFR use the prior otherwise-identical executable build.

### JFR of the bytecode interpreter on workload 2

`settings=profile`, guest compilation disabled, a three-second delayed start, same 50
functions/call sites and inner work; only the outer untimed round count is extended from
10 to 150. All rounds returned 3,620,400,000. The sampled event window is **22.23 s**,
with **2,124 main-thread guest execution samples** after excluding non-guest stacks and
other threads. Pre-run load: **4.57, 5.97, 4.84** (1/5/15 minutes).

Disjoint categories based on the top frames and inspected stacks:

| Remaining cost | Samples | Share |
|---|---:|---:|
| Operand-stack/local frame reads/writes/clears, frame initialization | 1,387 | **65.30%** |
| `PhpArray` lookup/hash/key normalization/COW | 373 | **17.56%** |
| Truffle call target argument/return profiling and call machinery | 210 | **9.89%** |
| Generated bytecode interpreter dispatch/handlers | 107 | 5.04% |
| Bytecode branch-profile writes | 45 | 2.12% |
| Other | 2 | 0.09% |

The frame-access classification is not an assumption that all `Unsafe` samples are array
work. Of the leaf samples, 1,019 were `Unsafe.putObject`, 241 `putLong`, 48 `putByte`, 45
`putInt`. Inspecting their callers showed:

```text
Unsafe.putObject → FrameWithoutBoxing.unsafePutObject → unsafeClear
  → FrameExtensionsUnsafe.clear → generated handleIndex_/handleCopy_/load handlers
Unsafe.putLong → FrameWithoutBoxing.unsafeSetBoolean
  → FrameExtensionsUnsafe.setBoolean → generated handleTruth$Bool$unboxed_
Unsafe.putInt → BytecodeDSLUncheckedAccess.writeInt → generated profileBranch
```

So the main remaining interpreter cost is **frame-backed operand-stack/local traffic**,
including clearing consumed object slots, not just the switch dispatch. Quickening does
eliminate primitive boxing between many opcodes, but calls still allocate frames and
arrays, and object operations must move/clear values.

Allocation samples independently support the frame diagnosis: weighted sampled allocation
is **29.52 GB of `long[]` (91.78%)**, all sampled with
`FrameWithoutBoxing.<init> → OptimizedCallTarget.createFrame` stacks; then **1.48 GB boxed
`Long` (4.60%)**, **0.53 GB `Object[]` (1.65%)**, **0.48 GB frame objects (1.51%)** and
**0.14 GB `byte[]` (0.45%)** during this deliberately repeated profile. These are JFR
**sample-weight estimates**, not exact allocation totals. There were **110 G1 collections**
with **101.07 ms** total recorded GC event duration—well below 1% of the sampled wall
window, so GC pause time was not the dominant residual bottleneck despite the allocation
volume. The production `PhpArray` methods remain boundaries and their key normalization/
hashing is shared by both paths.

Recording/full samples remain at
`/tmp/opencode/bytecode-spike/small-functions-bc.jfr` and
`/tmp/opencode/bytecode-spike/samples.json`; the checked-in
`bench/bytecode/profile-summary.json` contains the category counts, top leaves, allocation
weights and event timestamps. Percentages are sampled attribution, not exact CPU accounting.

`python3 bench/bytecode/measure.py --verify`. Both completed measurement batches also

committed only on `bytecode-spike`; nothing was pushed.
